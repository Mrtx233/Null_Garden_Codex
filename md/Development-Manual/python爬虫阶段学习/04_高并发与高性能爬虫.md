## 1. 并发理论基础

### 1.1 进程、线程与协程

并发的实现取决于调度层级的选择。Python 中涉及三个层级：进程（Process）、线程（Thread）与协程（Coroutine）。三者在内存模型、调度方式与适用任务上的差异如下。

```text
进程：操作系统调度的基本单位，拥有独立的内存空间与解释器实例
      进程间不共享数据，传递数据需要队列或管道
      适用于 CPU 密集型任务（计算、编解码、压缩）

线程：同一进程内的执行单元，线程之间共享进程的内存空间
      共享数据的修改需要加锁保护，否则产生数据竞争（Data Race）
      适用于 IO 密集型任务（网络请求、文件读写）
      受 GIL 限制，多个线程无法并行执行 Python 字节码

协程：用户态的轻量执行单元，由程序自身在单线程内完成切换
      不经过操作系统调度，切换开销最小
      适用于大量 IO 等待的任务，爬虫属于典型场景
```

代码层面的区别可归纳为三点：进程完全独立，各自持有内存；线程共享内存，需要注意数据竞争；协程在单线程内切换，不涉及系统调度，最为轻量。

### 1.2 IO 密集型与 CPU 密集型

任务按耗时来源分为两类，该分类直接决定并发方案的选择。

```python
import time

# IO 密集型任务（爬虫属于这一类）
# 耗时主要来自等待网络响应与磁盘读写，CPU 利用率低，瓶颈在 IO 速度

def io_task():
    time.sleep(1)  # 模拟一次网络请求，1 秒内均为等待状态
    return "数据"

# 串行执行 10 次，总耗时约 10 秒
# 并发执行 10 次同时发起请求，总耗时接近单次的 1 秒

# CPU 密集型任务（视频编码、科学计算）
# 耗时主要来自计算本身，CPU 处于满载状态

def cpu_task():
    total = 0
    for i in range(10**7):
        total += i
    return total

# 单线程执行时，多核机器仍然只使用一个核心
# 多进程执行时，各进程运行在不同核心上，总耗时随核心数下降
```

两类任务的特征与方案对应关系如下。

| 任务类型 | 耗时来源 | CPU 状态 | 可选方案 | 不推荐的方案 |
| --- | --- | --- | --- | --- |
| IO 密集型 | 等待网络与磁盘返回 | 利用率低 | 协程、多线程 | 多进程（进程多数时间空闲，资源浪费） |
| CPU 密集型 | 计算本身 | 满载 | 多进程 | 多线程（受 GIL 限制，无加速效果） |

### 1.3 全局解释器锁（GIL, Global Interpreter Lock）

```python
"""
GIL（Global Interpreter Lock，全局解释器锁）是 CPython 解释器的互斥锁：
同一时刻只有一个线程能够执行 Python 字节码。

由此得出两条结论：
1. 多线程在 CPU 密集型任务上没有加速效果，需要改用多进程绕过 GIL。
2. 线程在等待 IO 时会释放 GIL，其他线程可以在此期间执行，
   因此多线程对 IO 密集型的爬虫仍然有效。
"""
```

GIL 是 CPython 的实现细节而非语言规范，它使得共享状态的修改必须显式加锁。判断"多线程能否提高爬虫吞吐"的依据即在于此：爬虫的耗时集中在 IO 等待，GIL 在该阶段被释放，因此多线程有效。

### 1.4 同步与异步

```python
"""
同步（Synchronous）：发起操作后当前执行流阻塞等待结果，取得结果才继续执行后续步骤。

异步（Asynchronous）：同时发起多个操作，发起方不阻塞等待，
        任一操作就绪时由调度器恢复对应的处理逻辑。
"""
```

同步与异步的区别不在于是否使用多线程，而在于等待期间执行流是否被占用。爬虫的网络等待属于可让出的空闲时间，异步方案将这部分时间复用于发起其他请求，这正是其吞吐高于同步方案的原因。

- **要点**：进程独立内存、线程共享内存、协程在单线程内切换，三者的调度开销依次降低。
- **要点**：IO 密集型与 CPU 密集型的判定依据是耗时来源，即等待还是计算。
- **要点**：GIL 使多线程无法加速 CPU 密集型任务，但线程在 IO 等待期间会释放 GIL，因此多线程对爬虫有效。
- **要点**：异步的核心是等待期间让出执行流，将空闲时间复用于其他请求。

## 2. 多线程与线程池

### 2.1 threading 基础

`threading` 是标准库提供的线程模块，需要手动创建、启动并回收线程。

```python
import threading
import time

# 创建和启动线程
def fetch_url(url):
    print(f"开始请求: {url}")
    time.sleep(2)  # 模拟网络请求
    print(f"完成请求: {url}")

# 创建两个线程
t1 = threading.Thread(target=fetch_url, args=("https://a.com",))
t2 = threading.Thread(target=fetch_url, args=("https://b.com",))

# 启动线程
t1.start()
t2.start()

# 等待线程结束
t1.join()  # 阻塞至 t1 完成
t2.join()

print("全部完成")
# 两个请求并发执行，总耗时约 2 秒而非 4 秒
```

`Thread` 的常用参数为 `target`（执行函数）与 `args`（位置参数元组）；`start()` 将线程交由操作系统调度，`join()` 使主线程等待目标线程结束。

### 2.2 线程锁（Lock）与数据竞争

线程共享进程内存，多个线程修改同一变量时会产生数据竞争（Data Race），导致数据不一致。

```python
import threading

# 数据竞争的成因：counter += 1 由读取、计算、写回三步组成，
# 多个线程的这三步交叉执行时会丢失部分更新

counter = 0

def increment():
    global counter
    for _ in range(100000):
        counter += 1  # 该语句不是原子操作，多线程并发执行会产生数据竞争

threads = [threading.Thread(target=increment) for _ in range(10)]
for t in threads:
    t.start()
for t in threads:
    t.join()

print(counter)  # 结果小于 1000000，原因为数据竞争

# 使用互斥锁保证同一时刻只有一个线程进入临界区
counter = 0
lock = threading.Lock()

def safe_increment():
    global counter
    for _ in range(100000):
        with lock:  # 加锁期间其他线程无法进入该代码块
            counter += 1

threads = [threading.Thread(target=safe_increment) for _ in range(10)]
for t in threads:
    t.start()
for t in threads:
    t.join()

print(counter)  # 1000000，结果正确
```

### 2.3 线程安全的 URL 队列

爬虫中的共享状态通常是待抓取的 URL 列表。`queue.Queue` 内置锁机制，属于线程安全队列，可直接作为多消费者任务载体。

```python
# 爬虫实战：线程安全的 URL 队列
import queue
import threading
import time

q = queue.Queue()  # 线程安全的队列
q.put("https://example.com/page/1")
q.put("https://example.com/page/2")
q.put("https://example.com/page/3")

def worker():
    while not q.empty():
        url = q.get()
        print(f"处理: {url}")
        time.sleep(1)
        q.task_done()  # 标记该任务已处理完成

threads = [threading.Thread(target=worker) for _ in range(3)]
for t in threads:
    t.start()
q.join()  # 等待队列中所有任务处理完毕
print("所有 URL 处理完毕")
```

### 2.4 ThreadPoolExecutor（推荐方案）

手动管理线程需要处理创建、启动、回收与异常传播。线程池（Thread Pool）负责线程的分配与复用，调用方只需提交任务并收集结果。`concurrent.futures` 提供的 `ThreadPoolExecutor` 为此类场景的推荐方案。

```python
from concurrent.futures import ThreadPoolExecutor, as_completed
import time


# 基本用法
def fetch(url):
    print(f"请求: {url}")
    time.sleep(2)
    return f"{url} 的结果"


urls = [
    "https://a.com",
    "https://b.com",
    "https://c.com",
    "https://d.com",
    "https://e.com",
]

# 创建线程池（最多 3 个线程同时执行）
with ThreadPoolExecutor(max_workers=3) as executor:
    # 方式 1：submit 提交单个任务，返回 Future 对象
    futures = [executor.submit(fetch, url) for url in urls]

    for future in as_completed(futures):  # 按完成顺序返回结果
        result = future.result()
        print(f"拿到结果: {result}")

print("全部完成")

# 方式 2：map，写法更简洁，按传入顺序返回结果
with ThreadPoolExecutor(max_workers=3) as executor:
    results = executor.map(fetch, urls)
    for result in results:
        print(f"结果: {result}")
```

两种方式的选择依据为结果顺序要求：需要按提交顺序消费结果时使用 `map`；需要在任务完成时立即处理并统计进度时使用 `submit` 与 `as_completed`。

### 2.5 爬虫实战：多线程加速

线程池与 `requests.Session` 组合，可在保持连接复用的前提下提高抓取吞吐。

```python
"""
多线程爬虫：同时抓取多个页面
"""
from concurrent.futures import ThreadPoolExecutor, as_completed
import requests
import time


class ThreadPoolCrawler:
    """线程池爬虫"""

    def __init__(self, max_workers=5, timeout=10):
        self.max_workers = max_workers
        self.timeout = timeout
        self.session = requests.Session()
        self.session.headers.update({
            "User-Agent": "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36"
        })

    def fetch_one(self, url):
        """请求单个 URL"""
        try:
            start = time.time()
            resp = self.session.get(url, timeout=self.timeout)
            elapsed = time.time() - start
            return {
                "url": url,
                "status": resp.status_code,
                "size": len(resp.text),
                "time": round(elapsed, 2)
            }
        except Exception as e:
            return {"url": url, "error": str(e)}

    def fetch_many(self, urls):
        """并发请求多个 URL"""
        results = []
        start = time.time()

        with ThreadPoolExecutor(max_workers=self.max_workers) as executor:
            # 提交所有任务，并保留 Future 与 URL 的对应关系
            future_to_url = {executor.submit(self.fetch_one, url): url for url in urls}

            # 按完成顺序收集结果
            for future in as_completed(future_to_url):
                result = future.result()
                results.append(result)
                # 实时打印进度
                status = result.get("status", "ERROR")
                print(f"[{status}] {result['url']} ({result.get('time', '?')}s)")

        total_time = time.time() - start
        print(f"\n共 {len(urls)} 个请求，耗时 {total_time:.2f} 秒")
        print(f"平均每秒 {len(urls)/total_time:.1f} 个请求")

        return results


# 使用
# crawler = ThreadPoolCrawler(max_workers=10)
# urls = [f"https://example.com/page/{i}" for i in range(1, 51)]
# results = crawler.fetch_many(urls)
```

该类以单个 `requests.Session` 供全部线程共享，可复用底层 TCP 连接；`fetch_many` 返回的统计信息（总耗时、平均每秒请求数）用于评估吞吐。若目标站点校验连接级状态，则需按线程拆分 Session。

- **要点**：`threading.Thread` 需配合 `start()` 与 `join()` 使用，缺少 `join()` 时主线程会在子线程完成前退出。
- **要点**：`counter += 1` 属于读改写复合操作，修改共享变量需用 `threading.Lock` 保护临界区，`with lock` 在异常时仍会自动释放锁。
- **要点**：任务分发场景优先使用 `queue.Queue`，其自带线程安全保证，可配合 `task_done()` 与 `join()` 判断整体完成状态。
- **要点**：`submit` 配合 `as_completed` 按完成顺序处理结果，`map` 按提交顺序返回；`max_workers` 既是并发上限，也是对目标站点的保护阈值。
- **要点**：实战类共享 `requests.Session` 以复用 TCP 连接，异常在 `fetch_one` 内部捕获并写入返回字典，避免单个 URL 失败中断整个任务集。

## 3. 多进程与进程池

### 3.1 适用场景

```python
"""
多进程适用于 CPU 密集型任务（大量计算、编解码、压缩）。

爬虫中的应用场景：
1. 对抓取到的数据进行大量处理（如图片处理、数据清洗）
2. 爬虫需要执行 CPU 密集型操作（如解密、破解）
3. 需要绕过 GIL 限制，充分利用多核 CPU

对于请求发送本身即为耗时主体的纯 IO 型爬虫，多线程已经足够，无需引入多进程。
"""
```

多进程的代价是独立的内存开销与进程间数据序列化成本，因此仅在计算成为瓶颈时使用。

### 3.2 multiprocessing 基础

`Process` 的接口与 `Thread` 基本一致，区别在于其执行单元拥有独立内存空间。

```python
from multiprocessing import Process
import time

def work(name):
    print(f"进程 {name} 开始工作")
    time.sleep(2)
    print(f"进程 {name} 完成")

# 创建多进程，接口形式与多线程一致
processes = []
for i in range(4):
    p = Process(target=work, args=(i,))
    processes.append(p)
    p.start()

for p in processes:
    p.join()

print("所有进程完成")
```

在 Windows 与 macOS 上，多进程默认使用 spawn 启动方式，入口代码需置于 `if __name__ == "__main__":` 之内，否则子进程会重复执行顶层代码。

### 3.3 进程间通信（Queue）

进程不共享内存，数据传递需通过 `multiprocessing.Queue`。

```python
from multiprocessing import Process, Queue

# 进程间内存相互独立，数据传递需要通过 Queue

def producer(q):
    """生产者：向队列写入数据"""
    for i in range(10):
        q.put(f"数据 {i}")
    q.put(None)  # 写入结束信号

def consumer(q):
    """消费者：从队列读取数据"""
    while True:
        data = q.get()
        if data is None:
            break
        print(f"消费: {data}")

q = Queue()
p1 = Process(target=producer, args=(q,))
p2 = Process(target=consumer, args=(q,))

p1.start()
p2.start()
p1.join()
p2.join()
```

### 3.4 ProcessPoolExecutor

`ProcessPoolExecutor` 与 `ThreadPoolExecutor` 接口相同，将工作单元由线程替换为进程，从而绕过 GIL。

```python
from concurrent.futures import ProcessPoolExecutor
import time

# CPU 密集型任务
def cpu_heavy(n):
    total = 0
    for i in range(10**7):
        total += i
    return f"任务 {n} 完成，结果={total}"

# 多进程执行，充分利用多核 CPU
with ProcessPoolExecutor(max_workers=4) as executor:
    results = executor.map(cpu_heavy, range(8))
    for r in results:
        print(r)

# 爬虫中的混合使用：先多线程抓取，再多进程处理

def fetch_data(url):
    time.sleep(1)
    return f"{url} 的原始数据（体积较大）"

def process_data(data):
    """CPU 密集型处理（如解密、解压）"""
    time.sleep(2)  # 模拟耗时计算
    return f"处理后的: {data}"

# 阶段 1：多线程抓取，提高 IO 吞吐
from concurrent.futures import ThreadPoolExecutor
urls = [f"https://page/{i}" for i in range(20)]

with ThreadPoolExecutor(max_workers=10) as executor:
    raw_data = list(executor.map(fetch_data, urls))

# 阶段 2：多进程处理，提高计算吞吐
with ProcessPoolExecutor(max_workers=4) as executor:
    processed = list(executor.map(process_data, raw_data))

print(f"处理完成 {len(processed)} 条数据")
```

分阶段混合使用时，抓取阶段的瓶颈为 IO，处理阶段的瓶颈为计算，两个阶段分别选择与工作负载匹配的执行单元。

- **要点**：多进程用于 CPU 密集型任务，可绕过 GIL 并使用多核，代价为内存开销与数据序列化成本。
- **要点**：`Process` 与 `Thread` 接口一致，跨平台场景需将入口代码放入 `if __name__ == "__main__":`。
- **要点**：进程间通信使用 `multiprocessing.Queue`，示例中以 `None` 作为结束信号。
- **要点**：`ProcessPoolExecutor` 与 `ThreadPoolExecutor` 接口相同，可先多线程抓取、再多进程处理，分阶段匹配负载类型。

## 4. 异步协程（asyncio + aiohttp）

协程方案在单线程内实现并发，切换开销最小、可维持的并发连接数最高，是爬虫在大规模 URL 场景下的性能上限方案。

### 4.1 核心概念：协程与事件循环

```python
"""
async / await 是 Python 3.5+ 引入的语法关键字。

async def：定义协程函数（Coroutine Function），调用后返回协程对象，
          协程对象需交由事件循环执行，调用本身不会立即运行函数体。
await：在协程内挂起当前执行位置，向事件循环登记待完成的 IO 操作，并让出控制权。

事件循环（Event Loop）：协程的调度器
  - 持有并管理所有待执行的协程任务
  - 协程执行到 await 时被挂起，事件循环转而执行其他就绪的协程
  - 被挂起的操作完成后，事件循环恢复该协程 await 之后的代码
"""
```

上述机制的效果是：单线程内同时挂起大量等待中的请求，线程时间全部用于发起新请求与处理已就绪的响应，而非阻塞在单个 IO 上。

### 4.2 基础语法

```python
import asyncio


# 定义协程
async def say_hello():
    print("你好")
    await asyncio.sleep(1)  # 模拟异步等待，等待期间不阻塞事件循环
    print("世界")

# 运行协程
# asyncio.run(say_hello())  # 创建事件循环并在其中运行协程

# 用 asyncio.gather 并发执行
async def fetch_one(n):
    print(f"开始任务 {n}")
    await asyncio.sleep(1)  # 模拟网络请求
    print(f"完成 {n}")
    return f"结果 {n}"

async def main():
    # 并发执行 5 个任务，总耗时约 1 秒而非 5 秒
    tasks = [fetch_one(i) for i in range(5)]
    results = await asyncio.gather(*tasks)
    print(results)

# asyncio.run(main())

# 用 asyncio.create_task 创建后台任务
async def main2():
    # create_task 将协程注册为事件循环中的任务，立即开始调度
    task1 = asyncio.create_task(fetch_one(1))
    task2 = asyncio.create_task(fetch_one(2))

    # 等待任务完成并取回结果
    r1 = await task1
    r2 = await task2
    print(r1, r2)
```

`asyncio.run()` 是脚本入口，负责创建事件循环、运行主协程并在结束时关闭循环；`gather` 面向"批量提交、统一收集"的场景；`create_task` 面向"提交后按需等待"的场景，可在任务运行期间穿插其他逻辑。

```python
import asyncio
import aiohttp


# 基本用法
async def fetch(session, url):
    """单个请求"""
    async with session.get(url) as response:
        return await response.text()


async def main():
    # 创建 ClientSession，作用类似 requests.Session
    async with aiohttp.ClientSession() as session:
        html = await fetch(session, "https://example.com")
        print(f"获取到 {len(html)} 字节")


# asyncio.run(main())

# 并发请求
async def fetch_json(session, url):
    try:
        async with session.get(url, timeout=aiohttp.ClientTimeout(total=10)) as resp:
            if resp.status == 200:
                return await resp.json()
            else:
                return {"error": f"状态码 {resp.status}"}
    except Exception as e:
        return {"error": str(e)}


async def fetch_all(urls):
    """并发请求所有 URL"""
    # 设置请求头与超时
    headers = {"User-Agent": "Mozilla/5.0"}
    timeout = aiohttp.ClientTimeout(total=10)

    # 连接数限制，避免瞬时请求量超出目标站点承载能力
    connector = aiohttp.TCPConnector(
        limit=10,          # 总并发连接数
        limit_per_host=5,  # 同一主机的并发连接数
    )

    async with aiohttp.ClientSession(
        headers=headers,
        timeout=timeout,
        connector=connector,
    ) as session:
        tasks = [fetch_json(session, url) for url in urls]
        results = await asyncio.gather(*tasks)
        return results


# 使用
# urls = [f"https://api.example.com/page/{i}" for i in range(20)]
# results = asyncio.run(fetch_all(urls))
```

`ClientSession` 与 `TCPConnector` 应在整个任务期间复用：每次请求新建 Session 会重复建立 TCP 连接，抵消异步带来的收益。`limit_per_host` 是面向单一站点的主要保护阈值。

### 4.4 限制并发量（信号量 Semaphore）

```python
"""
并发不加限制时，瞬时提交 1000 个请求会触发目标站点的访问控制并导致 IP 被封禁。
信号量（Semaphore）用于限制同时执行的协程数量。
"""
import asyncio
import aiohttp


class RateLimitedCrawler:
    """带并发限制的异步爬虫"""

    def __init__(self, max_concurrent=10):
        self.max_concurrent = max_concurrent
        self.semaphore = asyncio.Semaphore(max_concurrent)
        self.results = []

    async def fetch_one(self, session, url):
        """带并发限制的请求"""
        async with self.semaphore:  # 并发数达到 max_concurrent 时后续协程在此等待
            try:
                print(f"请求: {url}")
                async with session.get(url, timeout=aiohttp.ClientTimeout(total=10)) as resp:
                    text = await resp.text()
                    self.results.append({
                        "url": url,
                        "status": resp.status,
                        "size": len(text),
                    })
                    return resp.status
            except Exception as e:
                print(f"失败: {url} - {e}")
                return None

    async def run(self, urls):
        headers = {"User-Agent": "Mozilla/5.0"}
        connector = aiohttp.TCPConnector(limit=self.max_concurrent)

        async with aiohttp.ClientSession(
            headers=headers,
            connector=connector,
        ) as session:
            tasks = [self.fetch_one(session, url) for url in urls]
            await asyncio.gather(*tasks)

        return self.results


# 使用
# crawler = RateLimitedCrawler(max_concurrent=10)
# urls = [f"https://example.com/page/{i}" for i in range(100)]
# results = asyncio.run(crawler.run(urls))
```

`asyncio.Semaphore` 在协程层面限制进入临界区的数量，`TCPConnector(limit=...)` 在连接层面形成第二重约束，两者数值应保持一致。

### 4.5 带重试与超时的完整异步爬虫

以下实现整合并发控制、超时处理、递增退避重试与结果落盘四个环节。

```python
"""
完整的异步爬虫：并发 + 重试 + 限速 + 错误处理
"""
import asyncio
import aiohttp
from typing import List, Dict, Any
import json


class AsyncCrawler:
    """异步爬虫"""

    def __init__(self, max_concurrent=10, retries=3):
        self.max_concurrent = max_concurrent
        self.retries = retries
        self.semaphore = asyncio.Semaphore(max_concurrent)

    async def fetch(
        self,
        session: aiohttp.ClientSession,
        url: str,
        **kwargs
    ) -> Dict[str, Any]:
        """带重试的请求"""
        last_error = None

        for attempt in range(1, self.retries + 1):
            async with self.semaphore:
                try:
                    async with session.get(url, **kwargs) as resp:
                        text = await resp.text()
                        return {
                            "url": url,
                            "status": resp.status,
                            "content": text,
                            "attempt": attempt,
                        }
                except asyncio.TimeoutError:
                    last_error = "超时"
                    print(f"超时 (第{attempt}次): {url}")
                except aiohttp.ClientError as e:
                    last_error = str(e)
                    print(f"请求失败 (第{attempt}次): {url} - {e}")

                if attempt < self.retries:
                    wait = attempt * 2  # 递增等待时间：2s、4s、6s
                    await asyncio.sleep(wait)

        return {
            "url": url,
            "status": 0,
            "content": None,
            "error": last_error,
            "attempt": self.retries,
        }

    async def run(self, urls: List[str]) -> List[Dict[str, Any]]:
        """并发抓取所有 URL"""
        headers = {
            "User-Agent": "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36",
        }
        timeout = aiohttp.ClientTimeout(total=30)
        connector = aiohttp.TCPConnector(limit=self.max_concurrent)

        async with aiohttp.ClientSession(
            headers=headers,
            timeout=timeout,
            connector=connector,
        ) as session:
            tasks = [self.fetch(session, url) for url in urls]
            results = await asyncio.gather(*tasks)

        return results

    def save(self, results, filename="async_results.json"):
        """保存结果"""
        with open(filename, "w", encoding="utf-8") as f:
            json.dump(results, f, ensure_ascii=False, indent=2)
        success = sum(1 for r in results if r["status"] == 200)
        print(f"成功 {success}/{len(results)}，已保存到 {filename}")


# 使用
async def main():
    crawler = AsyncCrawler(max_concurrent=20, retries=3)
    urls = [f"https://example.com/page/{i}" for i in range(50)]
    results = await crawler.run(urls)
    crawler.save(results)


# asyncio.run(main())
```

失败路径以 `status: 0` 与 `error` 字段返回，而非抛出异常，保证 `gather` 收集到与 URL 数量一致的结果列表；`attempt` 字段用于统计重试命中率并据此调整 `retries` 与超时配置。

- **要点**：`await` 让出控制权的前提是调用异步接口，协程内使用 `time.sleep()` 等阻塞调用会使整个事件循环停摆。
- **要点**：`asyncio.gather` 用于批量并发，`asyncio.create_task` 用于将协程注册为后台任务后按需等待。
- **要点**：`ClientSession` 与 `TCPConnector` 需全局复用，`limit` 与 `limit_per_host` 共同决定实际并发规模。
- **要点**：`asyncio.Semaphore` 控制同时执行的协程数，与 `TCPConnector(limit=...)` 构成协程层与连接层的双重限制，是防止 IP 被封禁的首要手段。
- **要点**：完整方案由超时、递增退避重试、并发限制与结果落盘四部分组成，失败项以标记字段返回而非中断任务。

## 5. 三种方案对比与选型

三种方案的维度对比如下。

| 维度 | 多线程（ThreadPoolExecutor） | 多进程（ProcessPoolExecutor） | 协程（asyncio + aiohttp） |
| --- | --- | --- | --- |
| 调度单位 | 操作系统线程 | 操作系统进程，各自持有独立解释器 | 单线程内的协程，由事件循环调度 |
| 切换开销 | 中等，涉及内核态切换 | 最高，进程创建与数据序列化成本高 | 最低，用户态函数挂起与恢复 |
| 适用任务类型 | IO 密集型 | CPU 密集型 | IO 密集型 |
| 内存占用 | 中等（线程共享进程内存） | 高（每个进程独立内存空间） | 极低 |
| 可支撑的并发数量 | 几十至几百 | 取决于 CPU 核心数 | 成千上万 |
| GIL 影响 | 受影响，IO 等待期间释放 GIL | 不受影响，进程各自独立 | 不受影响，单线程内仅有一个执行流 |
| 典型库 | `threading`、`concurrent.futures.ThreadPoolExecutor`、`requests` | `multiprocessing`、`concurrent.futures.ProcessPoolExecutor` | `asyncio`、`aiohttp` |
| 代码复杂度 | 简单 | 简单，需注意跨平台启动方式 | 中等，需理解 async/await 与事件循环 |
| 爬虫场景吞吐表现 | 高 | 低（IO 等待不占用 CPU，进程资源被浪费） | 最高 |
| 第三方库兼容 | 全部现有库可直接使用 | 全部现有库可直接使用，但参数与返回值需可序列化 | 需使用异步版本的库 |
| 注意事项 | 共享状态需加锁，`max_workers` 需显式设定 | 入口代码需置于 `if __name__ == "__main__":`；进程间传递数据有序列化开销 | 协程内不得调用阻塞函数，否则整个事件循环停摆 |

### 5.1 爬虫选型建议

```text
按场景选择：

  少量 URL（< 100 个）
    使用 requests + ThreadPoolExecutor，实现成本最低，吞吐满足需求

  大量 URL（> 1000 个）
    使用 asyncio + aiohttp，性能最优

  需要密集计算（解密、解压、图像处理）
    使用 ProcessPoolExecutor
```

实施顺序建议如下：

1. 先以 `requests` 加多线程实现，该方案改造成本最低，可快速验证采集流程。
2. 吞吐达不到要求时，将请求层替换为 `asyncio + aiohttp`。
3. 仅在出现 CPU 密集型处理环节时引入多进程，并与抓取阶段分阶段串联。

- **要点**：三种方案的取舍依据是耗时来源与目标并发规模，而非个人偏好。
- **要点**：协程方案性能最高，代价是要求异步版本的第三方库，且阻塞调用会拖垮整个事件循环。
- **要点**：多进程仅在计算成为瓶颈时使用，纯网络请求场景引入多进程反而浪费资源。
- **要点**：混合架构中多线程或协程负责抓取，多进程负责处理，两个阶段以队列或列表衔接。

## 6. 学习建议

1. **避免过早优化**：抓取规模为几十个页面时单线程已足够，并发方案应在吞吐成为瓶颈后引入。
2. **多线程优先使用 ThreadPoolExecutor**：线程的创建、回收与异常传播由线程池处理，`concurrent.futures` 的接口更安全且写法更简洁。
3. **协程是本阶段的最终方案**：`asyncio + aiohttp` 代表爬虫性能的上限，其学习曲线相对陡峭，可在第五阶段（Scrapy）之后深入理解，因为 Scrapy 的并发调度同样建立在事件循环模型之上。
4. **必须限制并发**：无论多线程还是协程，都需显式设定并发上限。100 个并发请求足以使小型站点服务不可用，同时导致本地 IP 被封禁。
5. **保持合规抓取**：设置请求间隔、控制并发数、遵守 `robots.txt`，属于爬虫实现的基本要求。

- **要点**：并发优化以实测吞吐为依据，在单线程方案达到瓶颈后引入。
- **要点**：协程知识与第五阶段 Scrapy 的事件循环模型直接对应，宜在其后系统深入。
- **要点**：并发上限、请求间隔与 `robots.txt` 三项控制在任何方案下均不可省略。

## 常见问题与排查

| 现象 | 原因 | 处理方式 |
| --- | --- | --- |
| 多线程统计结果小于预期（如计数器缺数） | 共享变量的读改写非原子，产生数据竞争 | 用 `threading.Lock` 保护临界区，或改用 `queue.Queue` 等线程安全结构分发任务 |
| 协程并发数量增大后总耗时未下降 | 协程内调用了 `time.sleep()`、`requests.get()` 等阻塞接口，事件循环被占满 | 改用 `asyncio.sleep()` 与 `aiohttp`，确保所有等待均为可让出的异步等待 |
| 大量协程报连接错误或对端拒绝 | 连接池耗尽，瞬时连接数超过 `TCPConnector` 与目标站点承载能力 | 设置 `limit` 与 `limit_per_host`，并用 `asyncio.Semaphore` 将并发压至可接受数值 |
| 多线程抓取 CPU 密集型任务无提速 | GIL 使同一时刻仅有一个线程执行 Python 字节码 | 该类任务改用 `ProcessPoolExecutor`，或拆分为"多线程抓取 + 多进程处理"两阶段 |
| 调用协程函数后无输出，提示 `coroutine was never awaited` | 协程函数调用只产生协程对象，未交予事件循环 | 在 `asyncio.run()` 内 `await`，或用 `create_task`/`gather` 注册任务 |
| Windows 下多进程报重复执行或序列化错误 | spawn 启动方式要求顶层入口保护，被传递函数与参数需可序列化 | 入口代码置于 `if __name__ == "__main__":`，仅传递模块级函数与可序列化参数 |
